# Отчёт по развёртыванию приложения в Kubernetes

## 1. Цель работы

Цель работы — развернуть приложение Task Manager в однодовом кластере Kubernetes, запущенном с использованием Minikube.

В процессе выполнения работы были решены следующие задачи:

- подготовлено Docker-окружение для приложения;
- создан Docker-образ приложения;
- запущен кластер Kubernetes с помощью Minikube;
- создан Docker-образ приложения и загружен в Minikube;
- подготовлены Kubernetes-манифесты для приложения и базы данных;
- развернуты приложение и PostgreSQL в Kubernetes;
- настроено взаимодействие приложения с базой данных;
- организован доступ к приложению из браузера;
- выполнено масштабирование приложения с одной до трёх реплик.

---

## 2. Описание приложения

Разворачиваемое приложение представляет собой веб-приложение Task Manager.

Приложение реализовано на Java с использованием Spring Boot. Для работы с базой данных используются Spring Data JPA и Hibernate. Управление изменениями структуры базы данных выполняется с помощью Flyway.

Основные компоненты приложения:

- Java 25;
- Spring Boot;
- Spring MVC;
- Spring Data JPA;
- Hibernate;
- Flyway;
- PostgreSQL;
- HTML, CSS и JavaScript для пользовательского интерфейса.

Приложение предоставляет веб-интерфейс для работы с задачами и REST API.

Приложение использует PostgreSQL для хранения данных.

# 4. Использованные абстракции Kubernetes

В процессе развёртывания были использованы следующие основные абстракции Kubernetes.

## 4.1. Pod

Pod является минимальной единицей выполнения приложения в Kubernetes.

В рамках данной работы Kubernetes создаёт:

- один Pod с PostgreSQL;
- один или несколько Pod с Task Manager в зависимости от количества реплик.

Изначально приложение запускалось с одной репликой:

```text
task-manager
└── Pod
```

После масштабирования:

```text
task-manager
├── Pod 1
├── Pod 2
└── Pod 3
```

Pod с PostgreSQL остаётся единственным:

```text
postgres
└── Pod
```

---

## 4.2. Deployment

Для запуска приложения и базы данных используются объекты `Deployment`.

### Deployment PostgreSQL

`postgres-deployment.yaml` создаёт Deployment с одной репликой PostgreSQL.

Основные параметры:

```yaml
replicas: 1
```

Контейнер использует образ:

```text
postgres:16
```

Для PostgreSQL задаются следующие параметры:

```text
POSTGRES_DB=taskdb
POSTGRES_USER=taskuser
POSTGRES_PASSWORD=taskpass
```

Deployment позволяет Kubernetes автоматически управлять Pod с базой данных и восстанавливать его в случае необходимости.

### Deployment Task Manager

`app-deployment.yaml` создаёт Deployment приложения.

Используется локально собранный образ:

```text
task-manager:1.0
```

Изначально Deployment создаётся с одной репликой:

```yaml
replicas: 1
```

После запуска приложения количество реплик было изменено командой:

```bash
kubectl scale deployment task-manager --replicas=3
```

В результате Kubernetes создал три Pod приложения.

---

## 4.3. Service

Для организации сетевого взаимодействия используются два объекта `Service`.

### postgres-service

Для PostgreSQL используется Service типа `ClusterIP`.

```text
postgres-service
```

Он доступен только внутри Kubernetes-кластера.

Приложение обращается к базе данных через DNS-имя Kubernetes Service:

```text
postgres-service:5432
```

Таким образом, приложению не требуется знать IP-адрес конкретного Pod PostgreSQL.

Строка подключения имеет вид:

```text
jdbc:postgresql://postgres-service:5432/taskdb
```

Использование Service позволяет сохранять стабильный адрес базы данных даже при изменении IP-адреса Pod.

### task-manager-service

Для приложения используется Service типа `NodePort`.

Он предоставляет доступ к Spring Boot-приложению из-за пределов кластера.

В процессе работы Kubernetes назначил NodePort:

```text
30734
```

Доступ к приложению был организован с помощью команды:

```bash
minikube service task-manager-service
```

Minikube открыл приложение в браузере через локальный адрес.

# 5. Взаимодействие сервисов приложения

Основное взаимодействие происходит между Spring Boot-приложением и PostgreSQL.

Пользователь взаимодействует с приложением через браузер.

Последовательность взаимодействия:

1. Пользователь открывает веб-интерфейс Task Manager.
2. Запрос поступает в `task-manager-service`.
3. Service передаёт запрос одному из Pod приложения.
4. Spring Boot обрабатывает запрос.
5. Для получения или изменения данных приложение обращается к PostgreSQL через `postgres-service`.
6. PostgreSQL выполняет операцию с базой данных.
7. Результат возвращается в Spring Boot.
8. Spring Boot возвращает результат пользователю.

Схематично:

```text
Браузер
   |
   v
task-manager-service
   |
   v
Task Manager Pod
   |
   | JDBC
   v
postgres-service
   |
   v
PostgreSQL Pod
```

# 6. Конфигурация подключения к PostgreSQL

В Kubernetes приложение получает настройки базы данных через переменные окружения.

Используются следующие значения:

```text
DB_URL=jdbc:postgresql://postgres-service:5432/taskdb
DB_USER=taskuser
DB_PASSWORD=taskpass
```

Важным отличием от локального запуска является использование имени Kubernetes Service вместо `localhost`.

При локальном запуске база данных может быть доступна по адресу:

```text
localhost:5432
```

Однако внутри Kubernetes `localhost` указывает на текущий Pod приложения. PostgreSQL находится в другом Pod, поэтому используется:

```text
postgres-service:5432
```

Kubernetes DNS автоматически разрешает имя `postgres-service` в адрес соответствующего Service.

# 7. Docker-образ приложения

Для приложения был создан `Dockerfile`.

Основой Docker-образа является:

```text
eclipse-temurin:25-jdk
```

Собранный Spring Boot JAR-файл копируется внутрь контейнера:

```text
target/task-manager-1.0.0.jar
```

Приложение запускается командой:

```text
java -jar app.jar
```

Контейнер использует порт:

```text
8080
```

Docker-образ был собран командой:

```bash
docker build -t task-manager:1.0 .
```

После этого образ был загружен в Minikube:

```bash
minikube image load task-manager:1.0
```

Проверка наличия образа выполнялась командой:

```bash
minikube image ls
```

В результате в Minikube присутствовал образ:

```text
docker.io/library/task-manager:1.0
```

Для Deployment приложения установлена политика:

```yaml
imagePullPolicy: Never
```

Это позволяет Kubernetes использовать локально загруженный в Minikube образ и не пытаться скачать его из внешнего registry.

# 9. Масштабирование приложения

Для демонстрации возможностей Kubernetes было выполнено масштабирование Task Manager.

Изначально Deployment имел одну реплику:

```text
task-manager
└── Pod
```

Для увеличения количества реплик была использована команда:

```bash
kubectl scale deployment task-manager --replicas=3
```

После выполнения команды состояние Deployment проверялось:

```bash
kubectl get deployment
```

Результат:

```text
NAME           READY   UP-TO-DATE   AVAILABLE
postgres       1/1     1            1
task-manager   3/3     3            3
```

Состояние Pod проверялось командой:

```bash
kubectl get pods
```

В результате было запущено три Pod приложения:

```text
task-manager-...   1/1   Running
task-manager-...   1/1   Running
task-manager-...   1/1   Running
```

Таким образом, Kubernetes автоматически создал дополнительные реплики приложения на основании заданного количества экземпляров Deployment.

# 10. Почему PostgreSQL не масштабировался

В данной работе PostgreSQL запускается с одной репликой.

Это связано с тем, что простое увеличение количества Pod PostgreSQL не является корректным способом масштабирования базы данных.

В отличие от Spring Boot-приложения, PostgreSQL хранит состояние приложения — данные задач.

Поэтому в рамках учебного проекта используется:

```text
PostgreSQL
1 Pod
```

а приложение является практически stateless и может быть запущено в нескольких экземплярах:

```text
Task Manager
3 Pod
```

Все экземпляры приложения используют одну базу данных через `postgres-service`.

kubectl scale deployment task-manager --replicas=3
