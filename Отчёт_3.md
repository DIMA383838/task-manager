# Отчёт по DZ3: сбор и анализ логов в Kubernetes

## 1. Цель работы

Развернуть Victoria Logs в кластере Minikube, настроить сбор логов приложения Task Manager в JSON-формате, выполнить запросы LogsQL и подключить Victoria Logs к Grafana.

## 2. JSON-логирование приложения

Для приложения Spring Boot настроено структурированное логирование в формате ECS. Формат JSON включён в `application.yml`.

В логах присутствуют следующие поля:
- `@timestamp` — время события;
- `log.level` — уровень логирования;
- `message` — текст сообщения;
- `service.name` — имя приложения;
- `log.logger` — источник сообщения;
- `process` — информация о процессе и потоке.

Формат проверен командой:

```powershell
kubectl logs deployment/task-manager --tail=10
```

В результате получены JSON-записи в stdout контейнера.

## 3. Развёртывание Victoria Logs и сбор логов

Victoria Logs Single установлен через Helm в namespace `logging`. Для сбора логов развёрнут `victoria-logs-collector` в виде DaemonSet.

Collector читает логи Kubernetes с узла Minikube и отправляет их в Victoria Logs через endpoint `/insert/native`.

Схема доставки:

```text
Task Manager
    ↓
stdout контейнера
    ↓
Логи Kubernetes
    ↓
Victoria Logs Collector
    ↓
Victoria Logs
    ↓
VMUI / Grafana
```

Работоспособность проверена в VMUI: после исправления URL доставки появились записи приложения Task Manager. В результатах отображаются Kubernetes-метаданные, включая имя Pod и namespace.

## 4. Запросы LogsQL

### 4.1. Просмотр логов за последние 10 минут

```text
_time:10m kubernetes.pod_name:task-manager*
```

Запрос отображает записи приложения Task Manager за последние 10 минут.

**Результат:** получены логи приложения с сообщениями Spring Boot.

*Скриншот 1 — сырые логи приложения.*

### 4.2. Фильтрация по уровню WARN

```text
_time:30m kubernetes.pod_name:task-manager* log.level:WARN
```

Запрос позволяет найти предупреждения приложения за последние 30 минут.

**Результат проверки:** найдено 2 записи уровня `WARN`.

*Скриншот 2 — фильтрация предупреждений.*

### 4.3. Подсчёт записей по уровням логирования

```text
_time:30m kubernetes.pod_name:task-manager* | stats by (log.level) count() logs
```

Запрос группирует записи по уровню логирования и подсчитывает их количество.

**Результат проверки:**

- `INFO` — 34 записи;
- `WARN` — 2 записи.

*Скриншот 3 — статистика по уровням логирования.*

### 4.4. Поиск наиболее часто встречающихся уровней

```text
_time:30m kubernetes.pod_name:task-manager* | top 10 by (log.level)
```

Запрос показывает наиболее часто встречающиеся значения поля `log.level`.

**Результат проверки:** `INFO` — 34 записи, `WARN` — 2 записи.

*Скриншот 4 — результат агрегирующего запроса top.*

## 5. Бонус: интеграция с Grafana

Grafana установлена в namespace `logging` через Helm. Подключён официальный плагин VictoriaLogs и настроен источник данных `VictoriaLogs`, указывающий на сервис Victoria Logs внутри кластера.

В Grafana Explore выполнен запрос:

```text
_time:30m kubernetes.pod_name:task-manager*
```

**Результат:** получены логи Task Manager, построен график объёма логов. Подключение к Victoria Logs проверено успешно.

*Скриншот 5 — логи Task Manager в Grafana Explore.*

## 6. Вывод

В ходе работы развёрнуты Victoria Logs и Grafana, настроен сбор логов Kubernetes через DaemonSet, проверено JSON-логирование Spring Boot и выполнены четыре запроса LogsQL. Интеграция Grafana с Victoria Logs также проверена на реальных логах приложения.
